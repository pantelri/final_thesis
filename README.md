# LLM-Based Completeness Verification of HGB Disclosure Obligations

**Repository:** https://github.com/pantelri/final_thesis

This repository contains the software artifacts, data pipelines, and empirical evaluation framework accompanying the Master's thesis on automated auditing of German financial statements and management reports (Jahresabschlüsse und Lageberichte) against statutory disclosure requirements under the German Commercial Code (Handelsgesetzbuch, HGB) and German Accounting Standards (Deutsche Rechnungslegungs Standards, DRS).

> **Note:** The repository includes components that were not used in the thesis (e.g., the optional RetrievalReviewModule and an optional majority-vote consolidation in the annotation platform).

The codebase is organized into two equally weighted pillars:

1. **Part I — HGB Annotation Platform (`annotation_app`):** A containerized web application designed for domain experts and auditors to annotate disclosure obligations, establish ground-truth evidence spans, and measure inter-annotator agreement across 182 audit cases (14 companies × 13 HGB disclosure obligations).
2. **Part II — Three-Stage RAG Audit Pipeline & Empirical Evaluation Framework:** The document ingestion workflow, the retrieval architecture, and a deterministic, multi-phase evaluation suite (Phases 1 to 7) assessing applicability classification, evidence retrieval, and fulfilment verification.

---

## Part I: HGB Annotation Platform (annotation_app)

The HGB Annotation Platform is a dedicated web application built with NiceGUI, PostgreSQL, SQLAlchemy, Docker Compose, and Caddy. It structures the expert labeling process into a conditional three-question audit mask (applicability assessment, passage-level evidence selection, and fulfilment verification) and supports multi-phase task assignment (coverage and inter-annotator agreement phases). An optional majority-vote consolidation exists but was not used in the thesis: the ground truth is not replaced by a majority vote.

### 1. Prerequisites

- Docker and Docker Compose (or Docker Desktop)
- Python 3.11+ (for running database seeding and import scripts outside Docker)

### 2. Environment Configuration

Navigate to the application directory and create the environment configuration file from the provided template:

```bash
cd annotation_app
cp .env.example .env
# Edit .env and set POSTGRES_PASSWORD, SECRET_KEY, and DATA_ROOT
```

Generate a cryptographically strong `SECRET_KEY` (at least 32 random bytes / 64 hex characters):

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

**Security Note (SECRET_KEY):** Annotator access-code hashes are derived deterministically via PBKDF2-SHA256 using `SECRET_KEY` as the cryptographic salt. Keep this key confidential and do not modify it once annotator accounts have been provisioned, as changing it invalidates all existing login credentials.

### 3. Database Initialization

Start the PostgreSQL service via Docker Compose:

```bash
docker compose up db -d
```

On initial startup with an empty PostgreSQL volume, the relational schema (`annotation_schema.sql`) is automatically initialized via `docker-entrypoint-initdb.d/`. To reset the database and re-apply the schema from scratch during local testing:

```bash
docker compose down -v   # Removes the pgdata volume and all stored records
docker compose up db -d
```

### 4. Data Import & Seeding

Install the local Python dependencies, create annotator access credentials, and populate the database with the 13 HGB obligations, 14 company reports, and pre-segmented text passages:

```bash
pip install -r requirements.txt

# Generate annotator accounts (outputs plaintext access codes to the console)
python -m scripts.seed_annotators

# Import obligations, company reports, and annotation items
python -m scripts.import_data
```

### 5. Running the Application

Start the web application either directly on the host or as a containerized service behind the Caddy reverse proxy:

```bash
# Option A: Run directly via Python
python -m app.main

# Option B: Run via Docker Compose (includes Caddy reverse proxy)
docker compose up app -d
```

The platform is accessible at http://localhost:8080 using the access codes generated by `seed_annotators.py`.

### 6. Production Deployment & Automated Backups

For deployment on a Linux virtual server (the thesis platform runs on a netcup server in Germany):

1. Clone the repository onto the target server and configure `.env` with production secrets and `DATA_ROOT`.
2. Update `Caddyfile` with the production domain name (Caddy provisions and renews TLS certificates automatically).
3. Launch the stack in detached mode:
   ```bash
   docker compose up -d
   ```
4. Configure automated daily database dumps via `crontab -e`:
   ```bash
   0 3 * * * docker exec annotation_app-db-1 pg_dump -U annotation annotation | gzip > /backups/annotation_$(date +\%Y\%m\%d).sql.gz
   ```

## Part II: Three-Stage RAG Audit Pipeline & Empirical Evaluation

The analytical core of the repository implements and evaluates a modular Three-Stage Retrieval-Augmented Generation (RAG) Architecture across the 182 company–obligation pairs:

* **Stage 1 — Relevance / Applicability Classification (RQ1):** Full-report assessment determining whether a statutory disclosure obligation is applicable to a given company (`relevant`, `not_relevant`, `unclear`).
* **Stage 2 — Evidence Retrieval (RQ2):** Extraction of relevant narrative passages and financial tables from the annual report via ChromaDB. Evaluated across a 2 × 2 × 2 × 4 factorial design:
  - **2 Embedding Models:** `google/gemini-embedding-001` (3072-d) vs. `qwen/qwen3-embedding-8b` (4096-d)
  - **2 Segmentation Strategies:** Sliding-window chunking (`chunk_text`, max. 701 characters) vs. sentence-aligned segmentation (`sentSeg`)
  - **2 Table Representations:** Raw Markdown tables (`raw_md`) vs. LLM-generated natural-language table descriptions (`llmdesc`)
  - **4 Query Formulations:** `zeroshot` (statute text), `enriched` (synthetic prototype passage), `oneshot`, and `twoshot`
  - No reranking step follows. The repository additionally contains an optional iterative LLM review agent (RetrievalReviewModule) capable of span-level refinement (`trim`, `remove_sentence`, `expand_neighbor`); it was not used in the thesis.
* **Stage 3 — Fulfilment Verification (RQ3 / H2):** Verification of whether the retrieved evidence fulfils the statutory requirement (`fulfilled`, `partially`, `not_fulfilled`), comparing predicted retrieval contexts against oracle ground-truth contexts as well as bare statutory text (`statute_only`) against enriched normative guidance (`web_enriched`).

### Evaluated Models

All generative evaluations and embeddings are executed via standardized OpenRouter API interfaces with deterministic caching:

* **Generative LLMs (Stages 1 & 3):**
  - `anthropic/claude-opus-4-8`
  - `google/gemini-3.1-pro-preview`
  - `qwen/qwen3.7-max`
  - `xiaomi/mimo-v2.5-pro`
* **Embedding Models (Stage 2):**
  - `google/gemini-embedding-001`
  - `qwen/qwen3-embedding-8b`

### 2. Document Ingestion & Corpus Preparation

The ingestion pipeline transforms raw PDF annual reports into structured Markdown while preserving atomic financial tables, segments the text into overlapping or sentence-aligned chunks, and generates synthetic retrieval queries:

```bash
# 1. Batch-convert PDF annual reports into structured Markdown via Adobe PDF Services
python batch_pdf_to_md.py

# 2. Validate chunking boundaries and character-offset consistency
python test_chunking.py Amazon_2024

# 3. Generate synthetic prototype passages (retrieval_text) for the 13 HGB obligations
python generate_enriched_requirements.py
```

Descriptive ground-truth analyses (span-length distributions, table prevalence, obligation overlaps, and unit tests) can be executed via:

```bash
python main_gt.py
python analyze_spans.py
pytest tests_gt.py -v
```

*Optional, not used in the thesis:* to interactively inspect the iterative retrieval-and-review agent (RetrievalReviewModule) on individual company–obligation pairs:

```bash
python retrieval_review.py
```

### 3. Reproducible Multi-Phase Evaluation Pipeline (scripts/eval/)

All empirical experiments reported in the thesis are orchestrated through a deterministic 7-phase evaluation pipeline (fixed random seed 42, Efron bootstrap with 1,000 resamples for 95% confidence intervals, and content-addressed response caching in `results/_qcache/`):

```bash
# Phase 1: Ground-Truth Sanity Checks & Canonical Retrieval Span Snapshot
python -m scripts.eval.phase1a_gt_sanity
python -m scripts.eval.phase1b_retrieval_gt

# Phase 2: Sentence-Aligned Corpus Construction, Table Summaries & ChromaDB Indexing
python -m scripts.eval.phase2_build_sentseg
python -m scripts.eval.phase2_table_summaries
python -m scripts.eval.phase2_embed --table-rep raw_md
python -m scripts.eval.phase2_embed --table-rep llmdesc

# Phase 3: Stage 2 Retrieval Evaluation (2x2x2x4 Factorial Grid, Recall@k, Hit@k, MRR)
python -m scripts.eval.phase3_retrieval

# Phase 4: Stage 1 (Relevance) & Stage 3 (Fulfilment) LLM Inference
python -m scripts.eval.phase4_web_enriched
python -m scripts.eval.phase4a_relevance
python -m scripts.eval.phase4b_fulfillment

# Phase 5: Statistical Aggregation, Bootstrap CIs & Pairwise Hypothesis Tests
python -m scripts.eval.phase5_relevance_metrics
python -m scripts.eval.phase5_fulfillment_metrics

# Phase 6: End-to-End Pipeline Evaluation & Oracle vs. Predicted Ablation Studies
python -m scripts.eval.phase6_end_to_end

# Phase 7: Automated Generation of Publication-Ready LaTeX Tables & Figures
python -m scripts.eval.phase7_export_latex_plots
```
